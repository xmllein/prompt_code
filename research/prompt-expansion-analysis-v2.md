# 提示词库第二轮扩展：场景与选材分析

日期：2026-11-01。以现有 26 个模板为基线，本轮继续核查 GitHub 的具体规则与技能文件，并结合工程经验分析覆盖缺口。**本轮仅新增研究文档，没有修改网页、模板 JSON 或已发布的 26 个模板。** 下文 F11–F24、B11–B24 都是候选编号，不表示已经上线。

## 1. 结论与范围

建议形成 **28 个专项候选（前端 14、后端 14）+ 8 项已有模板补强**，先从其中 12 个常见任务编写正式模板。优先级是按适用面、独立交付价值与当前覆盖情况做出的编辑判断，没有做模型效果排名或实际使用频率统计。

现有模板并非没有涉及这些要求。例如 F04 已有表单与竞态，B06 已有回调和幂等。专项模板的价值在于：用户遇到一个明确任务时，能直接选中完整流程，拿到特定输入、状态、失败路径和验收，而无需自行从多个大模板拼装。

一个候选值得独立成模板，至少满足以下条件：

1. 用户能明确说出触发场景，如“做订单表格”“接支付回调”。
2. 有区别于通用模板的必要输入和业务决策。
3. 有独立状态或失败机制，缺失时会导致实际问题。
4. 有可观察的完成标准；不能只要求“优雅、稳定、高性能”。

只有换框架名称、换角色、增加形容词的内容，不单独计数。技术栈与实际版本更适合作为参数或附加规则。

补充第一方依据：

- [TanStack Table v8：Row Selection](https://tanstack.com/table/v8/docs/guide/row-selection)：手动分页下，当前行模型只能生成传入数据的行；这说明跨页批量选择需要独立语义，不能把当前页面行模型当全部选中结果。这里特意链接 v8，不能把示例直接应用到其他大版本。
- [TanStack Query：Query Cancellation](https://tanstack.com/query/latest/docs/framework/react/guides/query-cancellation)：取消能力需要实际使用传入的 signal；“取消了查询”与“底层请求已经停止、不会覆盖状态”仍须分别验证。
- [tus resumable upload protocol](https://tus.io/protocols/resumable-upload)、[Uppy 上传器选择](https://uppy.io/docs/guides/choosing-uploader/)：恢复上传属于协议及客户端/服务端共同能力，不是一个进度条就能提供。

| B18 全文搜索、检索质量与索引同步 | 站内搜索、知识库、产品搜索 | 真实查询和期望、语言、权限、更新时效、引擎、质量/延迟目标 | 先评估关键词/全文是否足够；用标注查询衡量相关性；更新/删除/权限撤销传播可观测；重建切换可恢复 | 不把“返回很快”当搜索好用，也不默认所有搜索都要向量数据库 |
| B19 数据保留、归档、删除与恢复 | 用户数据长期持久化、注销、清理 | 副本/血缘、保留规则、软/硬删、备份窗口、删除时限、例外要求 | 主库/缓存/对象/搜索等传播删除；在途任务不复活；部分失败可追踪；历史恢复后重放删除；保留期由真实需求决定 | B03 的迁移与 B10 的恢复不单独证明完整数据生命周期 |
| B20 多步骤业务工作流与补偿 | 审批、预订、发货、跨外部服务流程 | 步骤依赖、状态、时限、人工介入、外部副作用、补偿语义 | 每步重复/超时/取消可恢复；补偿失败有处理；旧事件不推进新流程；恢复后不重复不可逆副作用；先评估普通状态机是否足够 | B05 是调度、B06 是消息处理，工作流要持久追踪跨步骤业务进度；Saga 提供选题线索，不是必须采用的方案 |
| B21 AI 服务成本、质量与故障控制 | 产品后端调用模型、RAG、工具型助手 | 供应商/核实的模型费率、质量样本、schema、预算粒度、流式与工具、留存 | 并发预算预留/结算、重试费、输出截断与 schema 错误、工具步数、取消后的实际费用、模型升级回归；比较达标任务成本 | 与 F09 的界面体验配对；不把减少 token 当作质量与总成本都改善 |
| B22 通知、邮件与消息触达 | 站内信、邮件、短信、推送 | 渠道、用户偏好/退订、优先级、频率、模板、供应商回执、去重范围 | 业务事件→渲染→提交供应商→回执状态可追踪；接受不等于已送达/已读；重复、退订、失败重试与渠道降级可验证 | B06 管队列语义；专项定义用户触达、偏好、频控和投递状态；仅为设计，不执行任何发送 |
| B23 指标统计、聚合与报表一致性 | 运营指标、排行榜、统计面板 | 指标口径、时间窗/时区、迟到/重复数据、实时性、查询负载 | 明确发生时间/入库时间；重算和补数幂等；迟到事件修正；总分项对账；查询不会拖垮交易库；按规模选择预聚合 | B08 只优化速度，专项先确认统计的是同一业务事实；不默认引入完整数据仓库 |
| B24 运行时配置、功能开关与灰度控制 | 按用户/租户开放功能、紧急关闭外部依赖 | 配置来源、作用范围、分组稳定性、版本、校验、传播延迟、回退默认 | 同一用户分组稳定；错误配置拒绝或降级；旧实例兼容；紧急关闭传播可观察；变更可审计；过期开关清理；前端开关不作授权 | B10 关注发布过程，专项定义运行中配置的读写与行为一致性 |

## 6. 为什么不能直接搬运仓库里的“最佳实践”

本轮实际发现了几类需要审阅的内容：

1. **版本和边界过度概括。** Copilot Next.js 规则把 server/client 组合概括得过于绝对。第一方文档明确区分客户端模块导入图与通过 props/children 传入的服务端输出，后者可以视觉嵌套。因此应提示模型读取实际版本与调用边界，不能只复制一句“不能这样组合”。[被核查规则](https://github.com/github/awesome-copilot/blob/main/instructions/nextjs.instructions.md)、[Next.js 第一方说明](https://nextjs.org/docs/app/getting-started/server-and-client-components)
2. **验证对象不同。** Copilot localization 文件针对 Markdown 翻译，不能拿它声称已经有应用级多语言、RTL、币种和时区方案。[原文件](https://github.com/github/awesome-copilot/blob/main/instructions/localization.instructions.md)
3. **示例遗漏并发保证。** 某 Webhook 样例先查是否处理、执行后再标记；两个请求可能同时通过检查。应分析原子领取、唯一约束、业务事务和外部副作用，而不是继承“只执行一次”的注释结论。[源文件](https://github.com/wshobson/agents/blob/main/plugins/payment-processing/skills/stripe-integration/references/details.md)
4. **示例常量不是通用参数。** 模型价格、token 阈值、缓存时长、并发数和虚拟列表阈值，必须来自业务目标、实际版本或测量。LLM 单进程费用记录也不能证明多实例不会超预算。[成本技能](https://github.com/affaan-m/ECC/blob/main/skills/cost-aware-llm-pipeline/SKILL.md)
5. **名称不能替代效果验证。** Vue 社区项目和 antfu 集合都主动注明实验/未充分验证的边界；它们适合帮助发现问题，不构成所有模型都能提高质量的保证。[Vue 项目说明](https://github.com/vuejs-ai/skills/blob/main/README.md)、[antfu 项目说明](https://github.com/antfu/skills/blob/main/README.md)

因此，扩展方式应是：从来源提取问题 → 核对项目与第一方语义 → 原创编写场景约束 → 用实际任务验证，而非把所有角色和规则原样拼进一条提示词。

## 7. 建议先编写的 12 个模板

首批建议是 **F11、F12、F13、F14、F16、F22，以及 B11、B12、B13、B14、B15、B16**。每个都需要能独立复制，同时允许轻量组合：

| 用户任务 | 前端与后端组合 | 验证重点 |
| --- | --- | --- |
| 做一个订单管理页面 | F11 + 现有 B02；存在扣减/预占时再加 B16 | 筛选与批量范围、并发不变量、重复提交 |
| 做文件上传和批量导入 | F14 + B14 + B15 | 上传完成与业务处理完成不同；坏行、重试、取消与下载权限 |
| 接入第三方登录 | B11 + B12 + F16 | 回调后恢复目的地、会话过期、刷新竞态、外部失败 |
| 支付回调后更新任务状态 | B13 + B16（实际涉及额度时）+ F17（需要实时显示时） | 验签、幂等、乱序、事务和界面最终同步 |
| 做知识库检索助手 | F13 + B18 + 现有 F09 + B21 | 搜索质量/权限、生成状态、来源、质量与预算 |

组合代表按任务阶段选择，不建议将多个完整模板不加裁剪地同时粘贴。也不应因为表里出现某组件，就为当前不需要它的产品增加基础设施。

## 8. 两个原创提示词结构示例

这些是说明专项深度的草案，没有加入当前网页。正式模板仍需统一工作约束、模式与项目上下文。

### 示例 A：复杂表格

```text
请处理这个列表页面：{{页面与主要用户操作}}。
执行模式：{{先分析 / 直接实施}}。
项目与版本：{{框架、组件库、表格库}}。
接口与数据：{{分页/筛选/排序契约、唯一ID、典型和峰值规模}}。
批量选择规则：{{只选当前页 / 跨页指定ID / 所有匹配结果}}。

先阅读现有页面与数据获取方式，明确列表状态由 URL、组件还是查询缓存持有。
把筛选、排序、分页、选择范围、批量操作和详情返回串成完整流程。
明确更换筛选、刷新数据、删除行和权限变化后，哪些选择保留、哪些失效。
处理旧请求覆盖、部分批量失败、空结果、失败恢复和长字段。
数据量足以构成瓶颈时再评估虚拟化，不能假定虚拟化自动解决服务端查询慢。
沿用现有设计系统，加载/更新不要无理由卸载整张表；键盘与窄屏下仍能完成主任务。

验收至少覆盖：跨页选择、切筛选、快速连续查询、批量部分失败、详情返回和实际数据规模。
分析模式给状态归属、关键取舍与实施切片；实施模式完成修改并汇报实际验证。
无法访问仓库或运行工具时，明确待核实项，不宣称已完成实测。
```

### 示例 B：Webhook 接收

```text
请处理 {{供应商与业务事件}} 的 Webhook 接收。
执行模式：{{先分析 / 直接实施}}。
协议文档与版本：{{链接或相关正文}}。
运行环境：{{框架、中间件、数据库、队列}}。
业务结果与不变量：{{收到事件应发生什么，什么不能重复发生}}。

先核对原始请求体验签、事件ID、时间窗口、响应期限、重试与乱序语义。
画出验签→可靠持久化→协议确认→处理→业务提交的时间线，分析各阶段崩溃。
并发重复事件不能靠“先查询再标记”获得幂等；按事务、唯一约束与原子状态转换设计。
区分本地数据库提交与外部副作用；外部结果不明时按供应商能力核对或补偿。
明确旧事件、重复投递、密钥轮换、无效事件、漏收回补与人工重放的处理。
不要用全局吞异常并返回成功掩盖事件丢失，也不要让慢业务处理无限占用接收请求。

验收包括：伪造签名、同事件并发、乱序、持久化失败、确认后崩溃、外部超时和重放。
分析模式给方案与保证边界；实施模式完成接入与有意义的故障验证。
按实际协议确定成功响应码和确认时机，报告证据，不宣称天然恰好执行一次。
```

## 9. 模板库和网页下一步可以怎样承载

当前 JSON 已有分类、标签、适用场景、默认模式、关联与来源，可承载上述候选。本轮只建议后续增补以下内容，不直接修改 schema 或界面：

- **明确触发信号**：例如“跨页批量选择不准”“回调重复扣减”，便于按真实问题搜索。
- **必要输入与可选输入**：只要求会改变方案的信息，不把每个小任务都变成架构调查。
- **前置条件/不适用情况**：如断点续传需要服务端协议支持，SEO 仅面向允许公开索引的页面。
- **结果与验收**：把成功、失败、中断、重复、并发及恢复按场景选择，避免全套强加。
- **来源与校核记录**：记录具体文件、阅读范围和适用版本；尚属工程推导的条目不伪装成仓库原文。
- **使用反馈**：记录实际任务是否一次完成、是否缺信息、是否过度设计、是否有证据，不以提示词长度或模板数量评估效果。

建议先将首批专项写成可独立复制的完整模板，拿真实开发任务试用，再决定是否把其余候选加入库。28 个候选是规划上限的一版清单，不是要求一次性上线全部内容。
